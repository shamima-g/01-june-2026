## 1. Goal

Enable an **Importer** to upload bank-transaction files into the system and an **Approver** to review, approve, reject, and export the resulting transactions, with a clear file-driven ingestion lifecycle and a per-transaction status flow that gates the available actions. The system operates in a South African financial-services context (ZAR currency, ZA-style account numbering) and is intended to replace manual handling of bank transaction files with an auditable, role-gated workflow. Every imported transaction must reach a terminal state (Approved or Rejected), with a mandatory rejection note captured when rejecting, ensuring a full audit trail.

## 5. Compliance

**Applicable domains:** `["popia"]`
**Region:** ZA (South Africa — inferred from ZAR currency throughout sample data and ZA-style 4-4-4 account numbering; consistent with requirements-2c.md §6.6.4)

### Compliance Requirements

- `[INFERRED]` **POPIA — Personal data handling:** the system processes User records (email, first name, last name) and transaction data linked to account numbers. A clear purpose statement must accompany any personal-data collection form; consent is obtained at account creation rather than at the transaction-import level (operator-to-operator context).
- `[INFERRED]` **POPIA — Data minimisation:** transaction screens expose account numbers and amounts only to authenticated operator personas (Importer, Approver). PII redaction on customer-facing surfaces is out of scope for this build (operators are the end users, not banking customers).
- `[INFERRED]` **POPIA — Data at rest and in transit:** personal data (email, name fields in User records) must be encrypted at rest and in transit (TLS 1.2+). This is an infrastructure-side obligation; the frontend enforces HTTPS-only communication via the Next.js proxy.
- `[INFERRED]` **POPIA — Audit trail:** every Approve and Reject action must be traceable to the acting user and timestamp. The `LastChangedUser` / `LastChangedDate` fields on Transaction records carry this trail. The UI must surface the rejection note and last-changed metadata on the Transaction detail view.
- `[INFERRED]` **POPIA — Right to access / erasure:** for the operator persona set, right-to-erasure is an infrastructure / DBA concern; the frontend provides no self-service data-deletion flow in this build. Flag for future sprint if regulator requires it.
- `[INFERRED]` **Audit-log retention:** requirements-2c.md §6.6.4 cites audit-log retention and data-residency policies as infrastructure-side obligations. The frontend does not implement a separate audit-log UI — the Transaction table's `LastChangedUser` / `LastChangedDate` columns serve as the visible audit surface.

## 7. Functional Requirements

- **R1:** When an unauthenticated user opens the application, the system presents an email-and-password login form and routes the authenticated user to their role-specific landing surface (Importer → Upload / File Log screen; Approver → Transactions table). Source: requirements-2c.md F-01, Flow: Authentication.
- **R2:** The system accepts file uploads for Importers via drag-and-drop or file picker; the upload requires `FileSettingId`, `FileSettingName`, and `FileName` attributes; the UI surfaces upload progress and explicit success or failure feedback. Source: requirements-2c.md F-02, F-03, Flow: File Upload.
- **R3:** The system creates a File Log per successful upload and lists all active File Logs in a table with columns: File Name, Process Date, Record Count, and File Status; clicking a row drills into that file's transactions. Source: requirements-2c.md F-03, F-04, Flow: File Log Overview.
- **R4:** The system lists Transactions in a sortable, paginated table (pagination: 5 / 10 / 20 / 50, default 20; single-column sort) with columns: Reference, Transaction Date, Account Number, Description, Amount, Currency, Transaction Type, and Status. Source: requirements-2c.md F-05, F-15, UF-01, UF-08.
- **R5:** The system supports filtering Transactions by Status (Imported / Approved / Rejected), File (FileLogId), Date range, Amount range, and free-text search on Reference and Account Number; active filters render as chips with a Clear-all action. Source: requirements-2c.md F-06, Flow: Search & Filter.
- **R6:** The system supports filtering File Logs by status, file name, and process date range. Source: requirements-2c.md F-07.
- **R7:** An Approver may approve a Transaction whose status is `Imported`; the action requires a confirmation modal naming the transaction reference; on confirmation the status transitions to `Approved` and the row updates immediately with a toast notification (auto-dismiss 4–8 s, top-right). Source: requirements-2c.md F-08, BR-01, BR-03, Flow: Approve Transaction.
- **R8:** An Approver may reject a Transaction whose status is `Imported` by submitting a non-empty Rejection Note (multi-line, max 500 chars); the submit control is disabled until a note is entered; on submission the status transitions to `Rejected` and the row updates immediately with a toast notification. Source: requirements-2c.md F-09, BR-02, BR-03, Flow: Reject Transaction.
- **R9:** An Approver may export the currently-filtered set of Transactions as a CSV file; the export reflects the active filter exactly; Export is disabled when zero rows match the current filter. Source: requirements-2c.md F-10, BR-06, Flow: Export Transactions.
- **R10:** The system surfaces a per-File Summary view showing Total records, Imported count, Approved count, and Rejected count; clicking a status count drills into the filtered slice of the Transactions table. Source: requirements-2c.md F-11, Flow: File Summary.
- **R11:** An Importer may retry validation on a `Failed` File Log; the system re-attempts processing and updates File Status; if re-validation fails again, the validation-error rows are refreshed with the updated count. Source: requirements-2c.md F-12, Flow: Retry Validation.
- **R12:** An Importer may cancel a File Log (triggering a destructive-action confirmation modal); on confirmation the File Log is deactivated and its Transactions are removed from the Approver's working surface; cancellation is blocked when any Transaction in the file is `Approved`. Source: requirements-2c.md F-13, BR-07, Flow: Cancel File.
- **R13:** The system surfaces validation errors on a `Failed` File Log as a list of invalid rows with column metadata (from `GET /v1/files/validation-errors` and `GET /v1/files/validation-errors/columns`). Source: requirements-2c.md F-14.
- **R14:** The File Logs table is sortable and paginated (5 / 10 / 20 / 50, default 20, single-column sort); pagination controls are always rendered (navigation disabled when dataset is smaller than current page size). Source: requirements-2c.md F-16, UF-08.
- **R15:** Empty states distinguish zero-data ("No file logs yet" / "No transactions yet") from zero-results-of-filter (active filter chips + Clear-all action, no creation CTA). Source: requirements-2c.md UF-07.
- **R16:** Status badges colour-map — `Imported` / `Processing` (blue), `Approved` / `Completed` (green), `Rejected` / `Failed` (red), `Uploaded` (grey/neutral) — colour is always paired with an icon or text label. Source: requirements-2c.md UF-09.
- **R17:** The session enforces a 15-minute idle timeout with a 60-second warning countdown; after 8 hours the session is terminated absolutely regardless of activity. Source: requirements-2c.md §6.6.1.
- **R18:** The login page distinguishes credential failures from connectivity failures in its error message and enforces account lockout after 5 failed attempts (15-minute cooldown). Source: requirements-2c.md §6.6.1, Flow: Authentication exception paths.

## 8. Business Rules

- **BR1:** When a Transaction's Status is not `Imported`, the Approve and Reject row-actions must be hidden in the UI (not disabled — hidden). Source: requirements-2c.md BR-01.
- **BR2:** When an Approver attempts to reject a Transaction, a non-empty Rejection Note must be submitted; the submit control is disabled until a note is entered; validate on blur and on submit. Source: requirements-2c.md BR-02.
- **BR3:** When an Approver approves or rejects a Transaction, a confirmation modal naming the transaction reference must appear before the status change is committed; for Approve, the primary action is destructive-styled; default focus is on Cancel. Source: requirements-2c.md BR-03.
- **BR4:** When a File Log's File Status is `Processing` or `Uploaded`, the row's drill-down must indicate work-in-progress and the Transactions table must surface a banner that the dataset is not yet final. Source: requirements-2c.md BR-04.
- **BR5:** When a File Log is in `Failed` status, the file detail must surface the validation-errors view and the retry-validation control (Importer-only); the Approver sees the validation-error list read-only without the retry control. Source: requirements-2c.md BR-05.
- **BR6:** When the Approver triggers Export, the exported row-set must equal the currently-applied filter set on the Transactions table. Source: requirements-2c.md BR-06.
- **BR7:** When a File Log has at least one `Approved` Transaction, the Cancel-File action must be blocked with an explanatory banner. Source: requirements-2c.md BR-07.
- **BR8:** When a Transaction's Status is `Rejected`, its Rejection Note must be visible on the Transaction detail view (read-only after rejection is committed). Source: requirements-2c.md BR-08.
- **BR9:** An Importer cannot access the Approve, Reject, or Export actions — these must be absent from the UI for the Importer persona (not hidden behind a disabled state). Source: requirements-2c.md §6.5.
- **BR10:** An Approver cannot access the Upload, Retry Validation, or Cancel File actions — these must be absent from the UI for the Approver persona. Source: requirements-2c.md §6.5.
- **BR11:** The Upload screen and the "Upload" top-level navigation item are visible only to the Importer; they are absent from the Approver's navigation. Source: requirements-2c.md UF-14, §6.5.
- **BR12:** On the File Log empty state, the Upload CTA is visible only to the Importer; the Approver sees the empty state without the Upload CTA. Source: requirements-2c.md Flow: File Log Overview, exception paths.

## 9. Key Workflows

### Authentication

1. User opens the application; the system detects no session and redirects to the login screen.
2. User enters email address and password.
3. The Next.js route handler proxies `POST /api/auth/login` → `http://localhost:10010/v1/auth/login` with body `{"Username": "<email>", "Password": "<password>"}`.
4. On 200: the session cookie is set; the frontend reads the user's role from the userinfo response (or from the login response payload) and routes to the role-specific landing (Importer → File Log / Upload surface; Approver → Transactions table).
5. On 401: inline error message distinguishing credential failure from connectivity failure.
6. On network error: connectivity-specific error state with a retry affordance.

### File Upload (Importer only)

1. Importer opens the Upload screen from top-level navigation.
2. Importer selects a file via drag-and-drop dropzone or file-picker fallback.
3. Importer provides (or the system pre-populates) `FileSettingId`, `FileSettingName`, and `FileName`.
4. Importer confirms upload.
5. The system sends `POST /api/transactions/v1/files/upload?FileSettingId=...&FileSettingName=...&FileName=...` with the file binary as `application/octet-stream`.
6. UI surfaces upload progress, then success or failure feedback.
7. On success: a new File Log is created; UI navigates or links to the File Log list showing the new entry.
8. On failure: error message with retry affordance.

### File Log Overview

1. User opens the Dashboard (File Logs list).
2. The system fetches `GET /api/transactions/v1/file-logs?IsActive=Yes`.
3. Table renders columns: File Name, Process Date, Record Count, File Status (derived from `LastExecutedActivityName` / `CurrentStatus`).
4. File Status `Failed` rows expose a Retry Validation control (Importer only).
5. User clicks a row to drill into that file's transactions.
6. Empty state: "No file logs yet" + Upload CTA (Importer only).

### Retry Validation (Importer only)

1. Importer identifies a `Failed` File Log in the list.
2. Importer opens the file detail and reviews the validation-error rows.
3. Importer clicks Retry Validation.
4. System sends `POST /api/transactions/v1/files/retry-validation?LogId=<id>`.
5. UI reflects updated File Status: `Completed` on success; `Failed` with refreshed error rows on continued failure.

### Cancel File (Importer only)

1. Importer opens the detail of a File Log that has no `Approved` Transactions.
2. Importer triggers Cancel.
3. Destructive-action confirmation modal appears: names the file, primary action styled as destructive, default focus on Cancel.
4. On confirmation: `DELETE /api/transactions/v1/files?LogId=<id>` (with `LastChangedUser` header).
5. File Log is deactivated; its Transactions disappear from the Approver's table.
6. If the file already has an `Approved` Transaction: action is blocked; explanatory banner is shown (BR7).

### Transaction Review (Approver primary surface)

1. Approver lands on the Transactions table after login.
2. System fetches `GET /api/transactions/v1/transactions`.
3. Approver applies filters (status, file, date range, amount range, free text).
4. Active filters render as chips; Clear-all resets filters.
5. Approver sorts by a column (single-column, ascending on first click; descending on second).
6. For each `Imported` row, Approve and Reject row-actions are visible.
7. For `Approved` or `Rejected` rows, row-actions are hidden.

### Approve Transaction

1. Approver clicks Approve on an `Imported` row.
2. Confirmation modal: "Approve transaction [Reference]?" — destructive-styled primary, default focus on Cancel.
3. Approver confirms.
4. System sends `POST /api/transactions/v1/transactions/approve?TransactionId=<id>` (with `LastChangedUser` header).
5. Row status flips to `Approved` immediately; toast notification auto-dismisses (4–8 s).
6. If concurrent change has already moved the row out of `Imported`: modal dismissed; banner explains new state.

### Reject Transaction

1. Approver clicks Reject on an `Imported` row.
2. Modal opens with mandatory Rejection Note text field (multi-line, max 500 chars, character counter).
3. Submit is disabled until a non-empty note is entered.
4. Approver enters note and submits.
5. System sends `POST /api/transactions/v1/transactions/reject?TransactionId=<id>` with body `{"UserNote": "<note>"}` (and `LastChangedUser` header).
6. Row status flips to `Rejected` immediately; toast notification auto-dismisses.
7. If note is empty on submit attempt: inline validation error; submit remains disabled.
8. If concurrent change: modal dismissed; banner explains new state.

### Export Transactions (Approver only)

1. Approver applies desired filters on the Transactions table.
2. Approver clicks Export in the toolbar.
3. CSV is generated client-side from the active filtered dataset (data already loaded from `GET /v1/transactions`).
4. File downloads with a name reflecting the active filter set and date.
5. If zero rows match the current filter: Export button is disabled with a tooltip explanation.

## 13. Notes & Caveats

### A — OpenAPI spec base URLs are stale

Both `documentation/auth-api.yaml` and `documentation/transactions-api.yaml` declare `servers[0].url: http://localhost:4423`. The running backend uses different ports: Auth API at `http://localhost:10010` and Transactions API at `http://localhost:10005/transactions-api` (with the path prefix as part of the base URL). The `backend-api/README.md` is the authoritative source for these addresses. A canonical `generated-docs/specs/api-spec.yaml` should be reconciled during BUILD — do not use the stale spec URLs in API client configuration.

### B — Endpoints not declared in the transactions-api.yaml spec

The running backend (verified by smoke test) serves endpoints that the OpenAPI spec partially or incompletely documents:

- `POST /v1/transactions/approve` and `POST /v1/transactions/reject` — **present in the spec** (added correctly); ensure the proxy route and API client use `?TransactionId=<id>` as a query param and `LastChangedUser` as a header.
- `POST /v1/files/upload` — **present in the spec** but uses query params (`FileSettingId`, `FileSettingName`, `FileName`) with an `application/octet-stream` body; verify this matches the live backend during BUILD.
- `GET /v1/file-logs` — **smoke-test returned 400**; the spec declares `?IsActive=Yes` as a required query param (type string, example `"Yes"`). The 400 was likely caused by a missing `IsActive` query param. The proxy must always pass `?IsActive=Yes` (or expose it as a filter) on this endpoint.

### C — PascalCase envelope drift (observed at runtime)

Live API responses wrap collections in a PascalCase single-key envelope rather than bare arrays. Confirmed for:
- `GET /v1/transactions` → `{"Transactions": [...]}`
- `GET /v1/users` → `{"Users": [...]}`

### D — TransactionType value format discrepancy

`requirements-2c.md §6.3` records `TransactionType` as single-character codes: `C` (Credit) / `D` (Debit), sourced from the sample CSV. ### E — GET /v1/auth/userinfo unconfirmed

### F — FileLog schema field naming (spec vs BRD)

### Fix role-name resolution against the live backend (post-launch bug)

Manual testing against the running backend surfaced a role-resolution defect. The live backend returns role **display-names** `"File Importer"` (importers) and `"Approver"` (approvers) — confirmed via `GET /v1/auth/userinfo` (which is now **confirmed live**: returns 200 with `Roles[].Name`, `Email`, and a `Pages[]` array) and `GET /v1/users`. But the app's `web/src/lib/auth/roles.ts` recognises only the exact canonical strings `"Importer"` / `"Approver"` (`KnownRole`, `LANDING_ROUTES`, `asKnownRole`, `readRole`). Consequently:

- An **Importer is not recognised** → `resolveLandingRoute` falls back to `/transactions` (so the Importer lands on the Approver surface instead of `/files`).
- Every **Importer-only affordance** gated on `asKnownRole(role) === 'Importer'` (Upload, Retry Validation, Cancel) is **hidden**, blocking the whole import pipeline through the UI.
- The Approver side works only because `"Approver"` happens to match exactly.

**Required:** introduce a mapping/alias from backend role display-names to the app's canonical `KnownRole` — `"File Importer"` → `Importer`, `"Approver"` → `Approver` — applied wherever a role is resolved/narrowed (`readRole` / `resolveLandingRoute` / `asKnownRole` / `fetchSignedInRole` / `fetchCurrentRole`), so role-based landing (R1) and all RBAC gating (BR9/BR10/BR11) work against the real backend. The alias should be tolerant (case-insensitive, trims/normalises) and easy to extend if more backend role names appear. Update the Vitest + Playwright role mocks to return the **real** backend names (e.g. `"File Importer"`) so the tests reflect production rather than the assumed shorthand, and add a regression test asserting `"File Importer"` resolves to the Importer landing (`/files`) and unlocks the Importer-only controls. No backend change; this is a frontend mapping fix.
